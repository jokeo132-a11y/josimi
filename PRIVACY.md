# Privacy and data handling

This document describes the v1.2.9 source and its intended Windows ZIP. Mining disclosures below apply only to the older v1.2.1 ZIP; v1.2.2 and later releases remove mining entirely. This document is based on source and configured release artifacts; it is not an independent privacy or security audit.

## Wallet and application data

josimi has no wallet-hosting account, telemetry service, or cloud backup feature. A packaged wallet normally lives under the `josimi/wallets/` directory beside the portable executable. Existing user-data wallets are preserved for compatibility, and a wallet opened through a selected `.keys` file remains at the path selected by the user. Backups are written only to the destination selected in the save dialog. When default-path creation or restoration replaces an existing wallet, its files are retained in a timestamped `josimi-wallet-before-restore-*` directory; the app does not automatically delete these archives. Identify and protect any retained copies, or remove them yourself after making the backup decisions you intend. The wallet database and its `.keys` file, backups, seed, and seed-offset passphrase are sensitive.

Seed display is an explicit user action protected by a localized native confirmation and a fresh current-wallet-password check. Password verification opens a temporary in-memory wallet from the existing key/cache data; it does not change the wallet files or provide operating-system-level reauthentication. The app clears temporary byte arrays and password references on a best-effort basis; JavaScript strings and runtime memory cannot be guaranteed physically zeroized. A password does not protect a seed displayed on screen, a compromised computer, or an exposed backup.

The Windows package contains the unmodified official `monerod.exe`, its required same-directory DLLs, the Monero license, an upstream notice, and a runtime manifest under `resources/app.asar.unpacked/assets/runtime/monero/`. It does not contain the full Monero CLI archive or the other CLI executables. The daemon files remain in the application resources; the app does not copy, extract, or download them at runtime. The pruned blockchain database and `monerod.log` are under the user-data `local-node/node/` directory. In the published v1.2.1 ZIP, XMRig and P2Pool data, including `p2pool.log`, were stored under the user-data `miner/` directory. v1.2.2 does not create or use that directory, but it does not automatically delete files left by an older installation. A durable relay-recovery file is stored in the user-data directory. It contains transaction hashes, a one-way hash of the wallet path, and recovery state; it does not contain wallet addresses, amounts, passwords, seeds, private keys, or signed transaction blobs.

## Monero node connections

The bundled local daemon is the default and starts automatically when the app opens. Its blockchain synchronization begins without a separate start click. Users can switch the remembered node choice to a public HTTPS daemon; in that mode the local daemon is not automatically started. Wallet creation makes a short, best-effort `get_info` request to capture an optional creation height; a node that is slow or unavailable does not prevent a new wallet from being created. Opening or restoring a wallet also does not wait for node readiness; wallet scanning starts automatically in the background and updates when the selected daemon responds. A public-node operator can observe the computer's IP address, connection timing, and wallet-related RPC request patterns. The app is designed not to send a seed or private spend key to a daemon. A public node remains a trust and privacy trade-off.

The Windows release build fetches the official Monero CLI v0.18.5.4 archive over HTTPS from `downloads.getmonero.org` as a temporary build input and checks its SHA-256 against the value pinned in project source. The build stages only `monerod.exe`, required same-directory DLLs, and license notices; it removes the temporary archive and excludes it and the other CLI tools from the final josimi ZIP. The app does not make a runtime network request to obtain Monero components or other external software. The bundled node downloads blockchain data over Monero P2P for initial and ongoing synchronization; this is not a software download and cannot be disabled while using the local node. Before launch, it checks the staged files against hashes in the included manifest. Those per-file hashes detect mismatches relative to the manifest, but the manifest is not independently signed. The release process also does not verify the source pin against Monero’s signed hash list. The daemon runs as a hidden process; no monerod console window is shown. Its administrative RPC binds to `127.0.0.1:18081`. The older v1.2.1 ZIP enabled a ZMQ publisher at `127.0.0.1:18083` for mining; v1.2.2 and later do not enable that publisher. The RPC has no application password, so other software running as the same user or malware on the computer may still access it. The daemon uses blockchain pruning, accepts pruned peer data with `--sync-pruned-blocks`, and disables router UPnP/IGD port mapping. It uses Monero v0.18.5.4's default fast database-sync mode, which switches to safe mode near the chain tip. A sudden power loss or system crash during the initial asynchronous phase may require checking or resynchronizing the blockchain database; wallet key files are separate. The daemon passes Monero's `--hide-my-port` option, which prevents the node from advertising itself as a peer-list candidate; this option does **not** stop the daemon from listening on its default P2P port (`18080`) on network interfaces. Incoming reachability therefore also depends on the computer's firewall and network; josimi does not configure firewall rules. The daemon continues outbound Monero P2P connections. The first sync can take hours or days and consume substantial disk space and bandwidth. The local daemon is stopped during normal app shutdown; it remains running when only the wallet is locked.

## Optional mining in the published v1.2.1 ZIP only

In v1.2.1, mining was off by default and started only after the user selected a mode and pressed Start. That release supported CPU mining only; GPU mining was not implemented. XMRig and P2Pool were bundled Windows runtimes whose executable hashes were checked before launch. XMRig's default developer donation was 1%; external pool fees and rules were controlled by those services. XMRig's accepted-share count was based on its log output, could include developer-donation shares, and did not prove that a pool credited or paid a reward to the user's wallet.

In direct-pool mode, XMRig connects to the configured Stratum endpoint and sends the computer's IP address, the wallet's public primary address as `-u`, and the configured pool password or worker value as `-p`. The MoneroOcean preset uses TLS at `gulf.moneroocean.stream:20128` and defaults to the worker value `josimi~rx/0`; users may edit that value. A custom pool can use plaintext Stratum when TLS is disabled. In that case, the wallet address and pool login/worker value are not encrypted and may be observed by network intermediaries. In automatic mode, josimi performs parallel TLS connection checks with a hard connection/handshake deadline and chooses the lowest-latency endpoint that completes the TLS handshake. Each candidate can see the computer's IP address and connection time, but the checks do not include the wallet address or mining shares; the selected pool later receives the normal XMRig login. The candidates currently configured are HashVault (`pool.hashvault.pro:443`), SupportXMR (`pool.supportxmr.com:443`), and MoneroOcean (`gulf.moneroocean.stream:20128`). A TLS handshake check does not validate pool login or guarantee that the pool will accept a share.

In local P2Pool mode, the bundled P2Pool process connects to the local monerod and receives the public primary wallet address as `--wallet`. XMRig connects only to P2Pool's loopback Stratum listener (`127.0.0.1:3333`); it receives neither the wallet address nor pool login credentials. Before starting XMRig, josimi checks the listener's P2Pool-specific local HTTP health response to avoid mistaking an ordinary unrelated service on port `3333` for P2Pool. This is an unauthenticated local marker check, not cryptographic or process-level identity proof, and it does not confirm completion of P2Pool's initial sharechain sync; P2Pool may remain in its own sync phase after the local monerod has synchronized. Upstream guidance says this first P2Pool sync normally takes about 5–10 minutes. The P2Pool command line can expose the address to local process-inspection tools, and it may appear in public P2Pool reward/share data or P2Pool logs. The P2Pool peer listener binds to all network interfaces on the profile's standard peer port: main `37889`, mini `37888`, or nano `37890`. Other peers may connect if the operating-system firewall and network permit it and can observe the node's IP and P2Pool activity. The app disables P2Pool UPnP port mapping; it does not create a router port-forwarding rule.

In solo mode, josimi sends the primary public address and mining settings to the local monerod's loopback-only `start_mining` RPC. Monero P2P peers can observe the node's IP and connection metadata. The app never sends the seed or private spend key to a mining pool, P2Pool, XMRig, or monerod.

The josimi service fee does not apply to mining rewards. It applies only to outgoing wallet transfers, as described below.

## Telemetry and limits

The reviewed application source does not intentionally send analytics or telemetry. This does not certify every dependency or runtime behavior, and the project has not received a formal independent security audit. GitHub release checksums detect accidental or mismatched files only when compared with a trusted copy of the checksum; they do not independently authenticate the publisher.
